## 标准格式

```markdown
### US-[编号]: [Story 标题]

**As a** [用户角色],
**I want** [做什么],
**So that** [为什么/得到什么价值].

**优先级:** [Must / Should / Could]
**模块:** [所属功能模块]
**关联页面:** [涉及的页面]

#### 验收标准 (Acceptance Criteria)

**Given** [前置条件],
**When** [用户操作],
**Then** [预期结果].

1. [ ] AC-1: [具体可测试的验收条件]
2. [ ] AC-2: [具体可测试的验收条件]
3. [ ] AC-3: [具体可测试的验收条件]

#### 备注
- [补充说明、边界情况、设计参考等]
```

## 验收标准编写指南

### 好的验收标准
- **具体可测试**: 任何人看了都能判断"通过/不通过"
- **独立**: 每条 AC 只测试一件事
- **完整**: 覆盖正常流程和异常流程

### 常见模式
- **正常路径**: 用户操作成功时的预期行为
- **异常路径**: 输入错误、网络失败等情况的处理
- **边界值**: 最大/最小值、空值、特殊字符等
- **权限**: 不同用户角色看到的内容不同

### 反面示例
- ❌ "页面看起来好看" — 不可测试
- ❌ "加载速度快" — 不够具体
- ✅ "页面在 3 秒内加载完成" — 可测试
- ✅ "用户名长度 2-20 个字符，超出时显示错误提示" — 可测试

## 优先级和估算

### 优先级对照
| 优先级 | PRD 对应 | 含义 |
|--------|----------|------|
| Must | Must Have | Sprint 内必须完成 |
| Should | Should Have | 尽量完成 |
| Could | Could Have | 有时间再做 |

### Story 拆分原则
- 一个 Story 应该足够小，能在一个 Sprint 内完成
- 如果 AC 超过 7 条，考虑拆分
- 按用户动作拆分，不按技术层拆分

## 示例

```markdown
### US-001: 用户注册

**As a** 新用户,
**I want** 注册一个账号,
**So that** 我可以使用 Pet Companionship 的所有功能.

**优先级:** Must
**模块:** 用户系统
**关联页面:** register.html

#### 验收标准

1. [ ] AC-1: 注册页面显示用户名、邮箱、密码、确认密码四个输入框
2. [ ] AC-2: 用户名长度 2-20 字符，仅允许字母、数字和下划线
3. [ ] AC-3: 邮箱必须是有效格式（包含 @ 和域名）
4. [ ] AC-4: 密码最少 8 位，包含大小写字母和数字
5. [ ] AC-5: 确认密码必须与密码一致，不一致时显示错误提示
6. [ ] AC-6: 邮箱已被注册时，显示"该邮箱已注册"提示
7. [ ] AC-7: 注册成功后自动跳转到登录页面

#### 备注
- UI 参考: UI_Reference/register.html
- 注册成功后发送验证邮件（Could Have，可后期添加）
```

```markdown
### US-002: 上传宠物照片

**As a** 已注册用户,
**I want** 上传我宠物的照片,
**So that** 系统可以生成我的虚拟宠物形象.

**优先级:** Must
**模块:** 宠物档案
**关联页面:** pet_profile.html

#### 验收标准

1. [ ] AC-1: 用户可以从相册选择或拍照上传宠物图片
2. [ ] AC-2: 支持 JPG、PNG 格式，文件大小不超过 10MB
3. [ ] AC-3: 上传时显示进度指示器
4. [ ] AC-4: 上传成功后显示图片预览
5. [ ] AC-5: 不支持的格式显示"请上传 JPG 或 PNG 格式的图片"
6. [ ] AC-6: 文件超过 10MB 显示"图片大小不能超过 10MB"

#### 备注
- 图片上传后后端需要存储原图和缩略图
- 后续会基于此图片生成 2D 动画宠物（属于桌面宠物模块的功能）
```
